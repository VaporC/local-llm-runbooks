# Qwen3.8-27B @ AI Max+ 395(实测评测)

> 一句话结论:和 RTX 篇正好相反——**27B 稠密在这台核显机器上就是慢,而且我们真装过、真用过后把它退役了。**
> 为追质量把量化从 Q4 提到 Q6/Q8,速度**腰斩到 ~16.5 t/s**,比同机的 35B MoE(~75)还慢一大截。原因很纯粹:
> 稠密模型每个 token 都要跑满 27B 参数、最吃显存带宽,而核显的统一内存带宽(~256GB/s)正是瓶颈。质量确实好,
> 但这台机器上稠密**快不起来**,最终被 Flash-Next 125B MoE 取代作生产。**想快 → 上 MoE;这张核显不该指望稠密 27B。**

---

## 一、测试环境

| 项 | 值 |
|---|---|
| GPU | AMD Ryzen AI Max+ 395(Strix Halo,gfx1151,核显 Radeon 8060S) |
| 内存 / 带宽 | 128GB 统一内存(~112GB 可用显存),LPDDR5X,**~256GB/s** |
| 引擎 | llama.cpp **Vulkan/RADV** 预编译版 b10448,router 多模型模式 |
| 模型 | Qwen3.8-27B(稠密,非 MoE),**Q6_K-mixed** 量化(imatrix 校准),含 MTP 草稿头 + mmproj 视觉头,abliterated 去审查改版 |
| 上下文配置 | 日常道 `--ctx-size 49152`(48K)+ MTP;长文道 `--ctx-size 262144`(256K)关 MTP |
| 对照组 | 同款 27B Q8 在 NVIDIA RTX PRO 6000 Blackwell(CUDA)上 |

**说明:27B 是稠密模型**(每 token 激活全部 27B 参数),和同系列的 Flash-Next(125B MoE 激活 6B)、35B-A3B(MoE 激活 3B)是完全不同的路子——稠密模型速度受显存带宽直接约束,而**核显的带宽正是短板**。这也是它在这台机器上表现最差的根本原因。

## 二、实测数据

| 指标 | 实测 | 备注 |
|---|---|---|
| 文本生成(Q6_K-mixed,日常道) | **~16.5 t/s** | MTP 开、48K 上下文;典型区间 16.5–22 |
| MTP 草稿接受率 | ~0.47 | 稠密天生比 MoE 低(同机 Flash-Next 达 0.80) |
| 视觉(看图/OCR 类) | **~20 t/s** | 发票图识别准确;多模态吞吐天然低于纯文本 |
| 长文道(关 MTP + 256K) | **~9 t/s** | 慢但稳,实证 12.5 万 token 不崩 |
| 显存占用 | ~27B 单模型部分,常驻组合 GTT ≈ 47GB | 稠密 27B 的 KV cache 不大 |

### 量化阶梯:追质量,把速度砍掉一半

27B 在本机的完整历程(3.6→3.8,同为 qwen35 稠密架构),这也是"太慢"的直接来源:

| 档位 | 实测 | 说明 |
|---|---|---|
| ① Q4_K_XL(首装,Qwen3.6-27B) | **~28 t/s**(冒烟 28.15) | 速度还行,但量化粗、质量打折 |
| ② Q8_0(为质量,Qwen3.6-27B 官方) | **~17.5 t/s**(接受率 0.67) | 近无损档,为质量上 Q8,速度立刻掉四成 |
| ③ Q6_K-mixed(最终,3.8 abliterated) | **~16.5 t/s**(接受率 0.47) | 甜点档:比自身 Q8 +17%,质量损失基准测不出 |

> **从 Q4 到 Q6/Q8,速度直接腰斩(28 → 16.5)。** 不是模型不行,是稠密 27B 在质量档位下,这台核显机器就只能跑这么快——而你要的恰恰是质量,没法靠降量化来换速度。
> 唯一的小便宜:同为高质量档,Q6_K-mixed 比 Q8_0 更划算("mixed" 把词嵌入/输出层保留 q8、只压中间层,拿测不出的质量损失换 +17% 速度)。

### 同机横向:稠密打不过 MoE

同一台 395、同一套 Vulkan 引擎跑过的四个模型,生成速度直接对比:

| 模型 | 架构 | 每 token 激活 | 生成速度 |
|---|---|---|---|
| PaddleOCR-VL 0.9B | 小模型 | 0.9B | **~240 t/s** |
| Qwen3.6-35B-A3B | MoE | ~3B | **~75 t/s** |
| Flash-Next 125B | MoE + MTP | ~6B | **~34 t/s** |
| **Qwen3.8-27B** | **稠密 + MTP** | **27B(全部)** | **~16.5 t/s** |

**反直觉但真实**:35B 参数比 27B 多却快 4.5 倍;125B 是 27B 的近 5 倍还快 1 倍。速度取决于**"每 token 实际激活多少参数"**,不是总参数量——MoE 每 token 只用一小部分专家,而 27B 稠密每 token 跑满 27B。**在这台核显上,稠密 27B 注定是最慢的一个。**

### 与 RTX PRO 6000 对照(同款 27B)

| 平台 | 文本速度 | 架构差异 |
|---|---|---|
| NVIDIA RTX PRO 6000(见 [RTX 篇](../rtx-pro-6000/qwen3.8-27b-review.md)) | **~95 t/s** | 独显 GDDR7,带宽 + FP 算力碾压 |
| **AMD AI Max+ 395(本文)** | **~16.5 t/s** | 核显 + 统一内存,**带宽是瓶颈** |

约 **5–6 倍差距**。27B 这种稠密模型对带宽极敏感,是**最能体现独显价值、也最能暴露核显短板**的负载类型。反过来,MoE 稀疏模型在核显上能"大而不慢"(见本目录的 [Flash-Next 125B runbook](./README.md)),差距就没这么夸张——**这正是这台机器最终选 MoE 而非稠密 27B 的原因**。

## 三、那个 55K 崩溃坑 + 双道方案

27B + MTP 在这台机器上有个硬伤,不了解会直接把 GPU 驱动搞崩(需重启整机)。

**根因:llama.cpp issue #27306** —— MTP 在**长上下文预填**时,每个批次会多跑一次草稿解码;累积到 **~5.5 万 token 必崩**,报 `vk::Queue::submit: ErrorDeviceLost`。这不是显存不够,是引擎缺陷。

对策是**双道**:

| 道 | 配置 | 用途 |
|---|---|---|
| 日常道 | MTP on,48K ctx | 压在崩溃线之下,享受 MTP 加速;深度分析、报告、代码 |
| 长文道 | **MTP off**,256K ctx | 关掉 MTP 就不触发这个 bug,实证 12.5 万 token 稳定;慢到 ~9 t/s,专供超长文档 |

外加两层兜底:GRUB `amdgpu.lockup_timeout=60000` 放宽内核超时;看门狗 timer 2 分钟内自愈。上游修复后可恢复单道 256K+MTP。

## 四、调参避坑:实测证伪清单

网上/社区流传的一些"优化",在这套 27B + Vulkan 组合上实测是**负优化或无效**(两个构建版本都验证过):

| 动作 | 网传 | 实测结果 |
|---|---|---|
| `spec-draft-n-max=4` | AMD 博客/社区推荐 | **负优化**。接受率 0.47→0.36,速度 14.2→13.3。保持默认 |
| 改用 ROCm 后端 | "ROCm 更快" | **更慢**。Vulkan/RADV 解码更快,已定为主线 |
| `GGML_VK_MAX_NODES_PER_SUBMIT=1` | 规避崩溃的偏方 | **无效**。issue 里已证伪,崩溃照旧 |
| 对标社区 22 t/s | "27B 能到 22" | 那是**官方原版 Q4_K_M**,量化档和模型版本都不同,不可比 |
| `reasoning-budget=0` 关思考 | 关思考提速 | 对此模型**无效**。改用 `chat_template_kwargs:{enable_thinking:false}`,抽取任务快 48 倍且不截断 |

## 五、想救速度试过什么:DFlash2(以及为什么放弃)

既然 27B 慢在"每 token 跑满 27B",自然会想:能不能用更强的投机解码把它拉起来?我们查证过 **DFlash2**。

- **是什么**:专为 Qwen3.8-27B 训练的 **1.92B 草稿模型**,号称在 **SGLang 上单并发吞吐达自回归的 3.4 倍**。
- **查证结果**:GGUF 版本确实有(z-lab / incoai 都发了);fork 引擎也带 `--spec-type draft-dflash` 选项,接口上支持。**但那个 3.4x 是 SGLang(NVIDIA 栈)上的数字**——在 llama.cpp / Vulkan / AMD 上能不能复现同样倍率,没人验证过,大概率打折。
- **最终决定**:与其赌 DFlash2 在 AMD 上能救回速度,不如换掉这个"天生慢"的稠密架构——上 **Flash-Next 125B MoE**,一步到位 34 t/s、能力更强、MTP 接受率还高达 0.80。**27B 就此退役。**

## 六、体验评价(主观,基于实际使用)

**优点**
- **质量确实好**:稠密 27B 的深度推理、长文写作、复杂代码质量,是它的核心价值;Q6_K-mixed 近无损,该有的都有。
- **视觉能力在**:挂了 mmproj 视觉头,发票/报表扫描件识别准确。
- **长文道兜底**:关 MTP 换 256K,超长文档能稳跑(实证 12.5 万 token)。

**代价 / 注意**
- **太慢**:16.5 t/s 对人读够用(比阅读快),但对 agent 批量/长任务明显偏慢,交互等待感重。
- **架构不占优**:稠密是核显上最吃亏的负载类型,同机 MoE 随便都比它快 2–5 倍。
- **有崩溃坑**:MTP 长预填 55K 崩(见第三节),必须靠双道 + 看门狗规避。

## 七、选型建议:这台机器上,27B 还是 MoE?

| 需求 | 选 |
|---|---|
| 就是要稠密的深度质量、能接受 ~16 t/s 慢、单人偶尔用 | Qwen3.8-27B(本文,但已不推荐作主力) |
| 日常吞吐、并发、agent 长任务、要快 | **35B-A3B MoE**(~75 t/s)或 **Flash-Next 125B**(~34 t/s,能力更强) |
| 高频批量 OCR / 票据识别 | 专用 OCR 模型(PaddleOCR-VL,~240 t/s) |

个人体感:**在核显机器上,稠密 27B 是"性价比最低的档"**——慢、吃亏、还有坑。它最大的用处反而是当**反面教材**:证明了"稠密吃带宽、核显是瓶颈"这条选型铁律。这台机器的正确答案是 MoE。
